# 競輪マルチビューアー（マルチビューの公開版）設計

2026-10-21 にオーナーと詰めた設計。元になったのは、Private のビューアにある「マルチビュー」（[docs/multiview.md](../../multiview.md)）。
「（Claude の判断）」と書いたものは、オーナーと話していない Claude の判断で、あとで変えてよい。

## 目的と背景

マルチビューは、複数の場の公式 YouTube ライブを1画面に並べて、タブを切り替えずに見るためのもの。
ミッドナイトなどで、3場ほどが数分おきに発走するときに使う。これを**ほかの競輪ファンにも使ってもらいたい**し、**ブログ記事のネタにもしたい**（オーナー）。

ただし、今のマルチビューはそのままでは公開できない。

- 開催の一覧と発走予定を keirin.jp の内部 API（`/pc/json`。robots.txt で許可されていない）から取っている。オーナーの私的な利用だから、控えめに使うという了承で使っているもの。
- 取ったデータを誰にでも見せると、KEIRIN.JP のサイトポリシーの「私的使用」を超える。
- 今のビューアは Private の keirin-data から、招待した人だけが見られる設定で動いている（Public にすることは禁止。docs/deploy-streamlit.md）。

そこで、**keirin.jp を一切使わず、YouTube だけで動く別のページ**として作る。

## 名前と置き場所（オーナー決定）

- 名前は「**競輪マルチビューアー**」。
- **新しい Public リポジトリ**に置き、GitHub Pages で公開する。
  - リポジトリ名は `keirin-platform/keirin-multiviewer`（Claude の判断。組織のリポジトリ名には `keirin-` を付けるルール）。
  - URL は `https://keirin-platform.github.io/keirin-multiviewer/`。
- 作り方は Streamlit ではなく、**静的な1枚の Web ページ（GitHub Pages）**にする（オーナー承認。Claude の提案）。理由は次の3つ。
  - Streamlit Community Cloud は、12時間アクセスがないと眠る。初めて来た人に起動ボタンの画面が出てしまう。
  - Streamlit 自体の余白が大きく、1画面に押し込みにくい。
  - 静的ページなら、見に来た人が増えても YouTube API のクォータを消費しない（下の「仕組み」）。

## 目標

- 開いただけで、今日の配信が並んで見られる（オーナー:「開いただけで配信画面を一覧で見られる状態なら便利」）。
- ノート PC（1440×900、ブラウザの表示域はおよそ 1440×790）で、**縦スクロールなしに4枠が収まる**。今のマルチビューでは2段目を見るのにスクロールが要る。公開版は情報を削るので、「無理やりにでも押し込めていい」（オーナー）。
- 今日配信している場から、映す場を選べる（最大4場）。

## やらないこと

- keirin.jp へのアクセス。開催の一覧、発走予定、出走表、結果、どれも使わない。
- 次に発走する場の強調、発走までの残り時間、「次の発走」の一覧。どれも keirin.jp の発走予定から作っていたため。締切や発走の時刻は配信の画面に出ていることが多いので、それで足りる（オーナー）。
- スマホやタブレット向けの画面（今のマルチビューと同じく、ノート PC が前提）。
- 出走表や予想を載せること、録画、見逃し再生。
- 収益化（広告、アフィリエイト）。CLAUDE.md の方針どおり。
- アクセス解析やクッキーによる追跡（Claude の判断。必要になったら相談する）。

## やってはいけないこと（動いても失敗とみなす）

今のマルチビューから引き継ぐもの:

- **音を自動で切り替える**こと。埋め込みはミュートで始め、音のオン・オフは YouTube のプレーヤーで使う人が行う。複数の枠を同時に鳴らしてもよい。
- **枠の大きさや位置が自動で変わる**こと。
- 場を足す・外す、データの更新などで、**残した枠の映像が読み込み直されて止まる**こと。
- YouTube のページを機械的に読み取ること（YouTube の利用規約に反する）。配信の検索は YouTube Data API だけで行う。

公開版で加わるもの:

- keirin.jp にアクセスすること（上の理由）。
- **API キーがページ、ログ、リポジトリに出る**こと。
- 公式のサイトに見えること。JKA や各場の公式ではないと分かるように書き、ロゴは使わない（Claude の判断）。

## 画面（オーナーが A 案を選んだ）

ブラウザで3案のモックを見せ、オーナーが「シンプルかつ機能性を失わない」として A 案を選んだ。

```
┌──────────────────────────────────────────────────────────────┐
│ 競輪マルチビューアー [松阪][川崎][四日市] 前橋  いわき平 …   URL を貼る │ ← 1行の帯
├───────────────────────────┬──────────────────────────┤
│ 松阪                       │ 川崎                      │
│        YouTube ライブ       │       YouTube ライブ       │
├───────────────────────────┼──────────────────────────┤
│ 四日市                     │ 空き枠                    │
│        YouTube ライブ       │ （上の場を押すと入る）      │
└───────────────────────────┴──────────────────────────┘
```

- 一番上に**1行の細い帯**を置く。左にタイトル、続けて**今日配信している場**をボタンで並べる。押すと枠に入り、もう一度押すと外れる。枠に入っている場のボタンは色を変える。
- 帯の下は **2×2 の固定グリッド**。各枠は 16:9 で、**表示域の高さに合わせて**大きさを決め、縦スクロールが出ないようにする。そのぶん左右に余白が出るのはよい。
  - 大きさは、ページを開いたときと、ウィンドウの大きさを変えたときにだけ決まる。場の選び直しやデータの更新では変わらない（Claude の判断。「枠の大きさが自動で変わらない」の解釈）。
- 場名は、映像の左上に小さく重ねる。枠の上の見出し行は作らない（Claude の判断。高さを稼ぐため）。
- 空いた枠には「上の場を押すと入る」とだけ出す。
- 4場が入っているときに5場目のボタンを押しても入らない（押せないように見せる）。
- 場を外して足したとき、**残した場の枠は動かさない**。新しい場は空いている枠に入る（今のマルチビューの `assign_slots` と同じ）。
- 帯の右端に「URL を貼る」を置く。YouTube の URL を貼ると、空いている枠（なければ、使う人が選んだ枠）にその配信が入る。
  照合はタイトル頼みなので、外れたときの逃げ道として残す。貼った URL は、そのページを開いている間だけ使う（Claude の判断。保存しない）。
- 帯かページの下のどこかに、目立たない形で次を載せる（Claude の判断）:
  - 非公式であること（各場の公式 YouTube 配信を埋め込んで並べているだけ）。
  - YouTube 利用規約へのリンクと、プライバシーポリシー（YouTube API Services の開発者ポリシーで、API のデータを使うアプリに求められる。下の「規約」）。
  - 配信の一覧を最後に更新した時刻。

### 最初の選択

- 開いた時点で、**ライブ中の配信を最大4つ**自動で入れておく。ライブ中が4つに満たないときは、予約中で開始が近い順に足す（Claude の判断）。
- 何を「ライブ中」とみなすかは、ページを開いたときのブラウザの時刻と、配信の開始時刻（実際の開始、なければ予定）で決める（Claude の判断。データの更新は1日数回なので、データの live フラグだけでは古くなる）。
- **終わった配信の扱い**（Claude の判断）: streams.json には配信の終わりの時刻がなく、終わった配信は次の検索の回まで残る。
  21〜22時台は、終わりかけのナイターと始まったミッドナイトが両方「ライブ中」に見える。主な使い道（ミッドナイト3場）を崩さないために:
  - 最初に入れる配信は、ライブ中のもののうち**開始が新しい順**に選ぶ（終わりかけの昼やナイターより、始まったばかりの開催が先に入る）。
  - 開始から **7時間**を過ぎた配信は、「終わっているかもしれない」として最初の選択に入れず、ボタンも薄く表示する（押せば入る）。開催の時間帯（モーニング・デイ・ナイター）は、配信の開始から最終レースまでおよそ4〜7時間なので。値は運用して調整してよい。
  - 夕方から夜の検索を増やす（下の「検索の回数」）。
  - 終わった配信が枠に入っても、YouTube のプレーヤーが終わった配信（見逃し）を表示するだけで、害はない。

### 今日配信している場のボタン

- 場名で並べる。並び順は開始時刻の順（Claude の判断）。
- ライブ中か予約中かと、開始時刻（予約中なら「19:30〜」など）が分かるようにする（Claude の判断。見た目は任せる）。
- 一度表示したボタンの並びは、ページを開いている間は変えない（「残した枠の映像を止めない」ため。新しい配信が見つかっても、ボタンの追加は末尾に足すだけにする）（Claude の判断）。

## 仕組み

```
GitHub Actions（cron、1日数回）
  └─ YouTube Data API で、全場の公式チャンネルから今日の配信を探す
  └─ streams.json を作り、index.html などと一緒に GitHub Pages へデプロイする
ブラウザ
  └─ index.html が streams.json を読み、YouTube の埋め込みプレーヤーを並べる
```

- **ページは HTML と JavaScript だけ**（サーバーなし）。ライブラリは使わなくてよい規模（Claude の判断）。
- **配信の検索は GitHub Actions が行う**。API キーは Actions の Secret（`YOUTUBE_API_KEY`）にだけ置く。ブラウザは API を呼ばないので、見に来た人が増えてもクォータは増えない。
  - Public リポジトリなので Actions の minutes は無料（keirin-data の minutes の上限には関係しない）。
  - Public リポジトリの Actions ログは誰でも見られる。キーを出さない（今の `YouTubeClient` はエラーにもキーを含めない）。
- **検索の回数**: 朝・昼・夕方に1回ずつと、ナイターが終わるころから1時間ごと（例: 07:13、12:13、16:13、19:13〜23:13 の毎時。JST。分は 0・30 からずらす）（Claude の判断）。
  - 配信は数日前から予約されているので、朝の1回で今日の分はほぼそろう。あとの回は、取りこぼしの補充と、終わった配信の除去のため。
  - GitHub の cron は数時間遅れることがある（CLAUDE.md 2026-10-07）。混んでいると、実行が落とされることもある（GitHub の文書）。
    - 予約配信は、時刻になると同じ動画 ID のままライブになる。一覧に入ってしまえば、発走に間に合うかどうかは検索の時刻と関係ない。
    - **一覧には、検索した日（JST）の「今日と明日」の配信を入れ、どの日の分を出すかはページがブラウザの時刻（JST）で選ぶ**（2026-10-22、オーナーの懸念を受けて追加）。
      前日のどこかの回が動いていれば、朝 07:13 の回が数時間遅れても、モーニングの配信まで入っている。
    - 終わった配信の除去が遅れる分は、上の「終わった配信の扱い」で吸収する。
  - ワークフローの `concurrency`（group: pages）では、実行中の回があるときに待っている回は1つだけになり、新しい回が来ると古い待ちの回は取り消される。
    検索は毎回同じことをする（前の回の結果に頼らない）ので、取り消されても失うものはない。
  - クォータは1日9回で約900 ユニット。
- **cron の自動停止への対策**（Claude の判断）: Public リポジトリの schedule は、リポジトリに60日間動きがないと GitHub が止める。streams.json をコミットしないので、放っておくと止まる。
  - コミットはせず、ワークフロー自身が GitHub の API でワークフローを有効にし直して止まらないようにする（keepalive。コミットを作らないので、署名のルールとぶつからない）。具体的な方法は任せる。
  - あわせて、一覧が今日の分を含まなくなったら（作成した日が、JST で昨日より前）、帯に小さく「配信の一覧が古い可能性があります」と出す。
- **探し方**: 今の `keirin.youtube` を使う。チャンネル一覧、タイトルから場への照合（施行者の表記、「X in Y」、別名、「予想」の除外）、同じ場に候補が複数あるときは実際の場の公式チャンネルを優先、はそのまま。
  - **違うところ**: 今は keirin.jp の「今日開催している場」で探すチャンネルを絞り、照合の候補にも使っている。公式版では、**全場のチャンネル（47）を毎回探し、照合の候補も全場**にする。発走予定の時間帯での絞り込みもなくし、JST で今日・明日に始まる（または今ライブ中の）配信を残す。
  - クォータ: 1回で playlistItems 47 ユニット ＋ videos 約47 ユニット（50件ずつ）＝ 約100 ユニット。1日4回で約400 ユニット。無料枠の 10,000 に十分収まる。
  - **ここが一番外れやすい**。今は開催していない場はそもそも候補にならなかったが、公開版では、レースではないライブ（トークショーなど。「予想」を含まないもの）が、そのチャンネルの場として出てしまうおそれがある。最初は現状の照合のまま出して、外れが見つかったら除外語を足す（Claude の判断）。
- **コードの共有**: 新しいリポジトリの Actions は、keirin-platform を **コミット SHA で固定して** pip で入れ、`keirin.youtube` を使う（Claude の判断。keirin-data が requirements.txt でやっているのと同じ形）。
  公開版に要る変更（全場を探す入り口、時間帯の絞り込みをしない照合）は keirin-platform 側に足す。Private のビューアのマルチビューの動きは変えない。
- **streams.json はリポジトリにコミットしない**。Pages の成果物として毎回デプロイするだけにする（Claude の判断）。
  YouTube の開発者ポリシーは API のデータを長く保存することを制限しているので、git の履歴に積み上げない。リポジトリに残るのはコード（チャンネル一覧などの設定を含む）だけ。
- streams.json の中身は、日（JST）と場ごとに1件: 日、場コード、場名、動画 ID、タイトル、開始時刻（実際の開始か予定）、ライブ中かどうか、それに作成時刻（Claude の判断）。
  ライブ中の配信は、前日に始まったものでも「今日」に入れる。
- 検索が失敗したとき（クォータ切れ、ネットワーク）は、**前のデプロイを残す**（デプロイしない）。ページでは「最後に更新した時刻」が古いことで分かる（Claude の判断）。
- 埋め込みは今と同じく `autoplay=1&mute=1&playsinline=1`。

## 規約

- **YouTube API Services の開発者ポリシー**: API のデータを使うアプリは、YouTube 利用規約への同意を求める表示（利用規約へのリンク）と、プライバシーポリシーを載せる。公開前に、ポリシーの最新の文面を確かめる。
  プライバシーポリシーは「このページは個人情報を集めない。埋め込みの YouTube プレーヤーは YouTube（Google）のポリシーに従う」程度の短いものでよい（Claude の判断）。
- YouTube の埋め込みプレーヤーをそのまま使う（プレーヤーの上に要素を重ねて操作を妨げない。場名のラベルは隅に小さく、クリックを奪わない）。
- 各場の配信は、各場が YouTube で公開しているもので、埋め込みは許可されている（`playableInEmbed`）。埋め込みを無効にしている配信があれば、その枠は YouTube 側のエラー表示になるだけでよい。
- KEIRIN.JP には一切アクセスしないので、サイトポリシーと robots.txt の制約はかからない。記事からこのページへリンクしてよい（「ビューアや Private リポジトリにはリンクしない」の例外として CLAUDE.md に書く）。

## テストと確認

- Python 側（全場を探す入り口、照合）は、今と同じく**架空の API レスポンス**でテストする。実データや実際のキーを使わない。
  照合のテストに、「開催していない場のチャンネルのレース以外のライブ」の形を加える。
- ページは、架空の streams.json を置いてブラウザ（ヘッドレスの Chromium）で確かめる:
  - 1440×790 の表示域で、縦スクロールが出ずに4枠が収まる。
  - 場を外す、足す、4場まで入れる、URL を貼る、のどれでも、残した枠の映像の要素が作り直されない（読み込み直しが0回）。
- 実際のキーで、Actions を手動実行（workflow_dispatch）して起動まで確かめる（CLAUDE.md の開発ルール）。今夜の配信が正しく出るかを見る。

## 実装に任せること

- 帯とボタンの見た目、色、ライブ中・予約中の見せ方、空き枠の文言。
- 枠の大きさの計算方法（CSS だけでも、JavaScript でもよい）。
- ページから streams.json を読み直すかどうか（読み直すなら、ボタンの並びと残した枠を動かさないこと）。
- 検索の時刻と回数（上は例）。
- streams.json の形。
- リポジトリの README（何をするページか、非公式であること、キーは Secret に置くこと）。
