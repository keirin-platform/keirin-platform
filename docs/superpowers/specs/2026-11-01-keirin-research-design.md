# 競輪の共通認識リポジトリ（keirin-research）設計書

- 日付: 2026-11-01
- 状態: 草案（オーナー承認前）
- 置き場所: 新しい Public リポジトリ `keirin-platform/keirin-research`（手元では `~/github/keirin-platform/keirin-research`）
- 下敷き: オートレースの `~/github/autorace/autorace-research`（設計書は同リポジトリの `docs/superpowers/specs/2026-10-19-verification-framework-design.md`）

## 1. なぜ作るか

AI が持つ競輪の知識は、実用的とは言えない水準にある。予想を作らせると、まず選手ごとの単純な連対率から組み立ててしまう。
「同じラインの1人が上位に来ると、ラインの別の選手も上位に来やすい」というラインの連動は、オーナーが作業を繰り返す中で自分で気づいて、AI に持ち込んだ。
これは競輪ファンなら当然知っている前提で、AI には作業を始める時点で知っていてほしい（オーナー）。

keirin-platform では、ほかにもドメインの知見が積み上がっている。ただし、それぞれが別の場所にある。

- CLAUDE.md の「分析するときの前提」（車番の付け方: ミッドナイトは得点順、4・6・8番車の慣例）
- docs/keirin-theories.md（通説の一覧と、文献の根拠、22日分の簡易集計）
- docs/score-correction.md（得点の窓、昇降級の Δ）
- docs/prediction.md（ライン効果、試したが効かなかった特徴）
- docs/lines.md と docs/data-schema.md（並びの取得元と性質）
- CLAUDE.md の「オーナーの要望」10.（雨・強風の個人差の試算）

どれも、実装のメモや経緯の記録と混ざっている。そのため、検証を設計する時点で必要な知識が確実には呼び出されない。
しかも keirin-platform の中にあるので、keirin-blog やこれから作るリポジトリからは使えない。

そこで、競輪の共通認識を、keirin-platform から独立したリポジトリにまとめる。中身は、検証で確かめた法則と、公式の資料で確かめた規則・事実。
**データがまだ揃い切っていない段階から始めて、データが増えるのに合わせて少しずつ登録を増やしていく**。この点が autorace-research と違う。
autorace-research は、巨大な DB で検証を回し終えた知見を抜き出したものだった。

## 2. 防ぎたい失敗（実例）

| # | 型 | 実例 | 仕組みに求めること |
|---|---|---|---|
| F1 | 要因の見落とし | 単純な連対率で予想を組み立てた。ラインの連動は、オーナーが繰り返しの中で気づいて持ち込んだ（オーナー） | 作業を始める前に、レースの仕組み（ライン、位置、主導権）から要因を挙げさせる |
| F2 | 配置と効果の取り違え | 「1番車有利」「4・6・8番車は来ない」は、車番の位置の効果ではない。ミッドナイトは得点順に1番車から並び、4・6・8番車には相方より弱い選手を置く慣例がある。ここから来る実力の配置の効果だった（CLAUDE.md。慣例はオーナーの指摘） | 番組編成の規則と慣例を持ち、比べる前に実力をそろえさせる |
| F3 | 尺度の取り違え | 競走得点は、級班をまたぐと同じ尺度にならない（昇降級の Δ。窓は当月＋前3ヶ月） | 項目の意味と成立期間を持たせる |
| F4 | 交絡の見落とし | 「初日は逃げ切りが多い」を疲労の証拠と読みかけた。実際は、初日に予選が多いことによる（docs/keirin-theories.md） | 種目、車立て、時間帯、級班の構成をそろえさせる |
| F5 | 検出力不足の読み違え | 雨・風の個人差は p=0.65 / 0.32 で偶然の範囲内だった。ただし選手あたりの雨の走数が十数走しかなく、「差がない」とは言えない（CLAUDE.md の要望10.） | 「有意でない」を「差がない」と書かせない。判断できないものは保留にする |
| F6 | 取得元の性質の見落とし | 並びはレース前の**予想**で、実際の隊列ではない。本物の並びがある期間は限られていて、それ以外は府県から**推定した**並びになる。周回ごとの位置はデータにない | 取得元ごとの性質と、データから見えないものを持たせる |

F2〜F6 は、keirin-platform で実際に起きたか、起きかけたもの。設計者がドキュメントから拾った。

## 3. ゴール

- **G1** AI が競輪の作業（予想、分析、記事の下調べ）を始める時点で、ラインなどの基本を知っている。
- **G2** F1〜F6 を、作業の設計と結論の段階で AI が自分で拾う。
- **G3** 広く知られている法則を自分たちのデータで確かめ、確かめたものだけを登録する仕組みにする。データが増えたら、保留にしたものを確かめ直して登録できる。
- **G4** 「選手の個人差がある／ない」という知見を、選手の名前を出さずに登録できる（今後の拡張の主な方向。オーナー）。
- **G5** Claude Code で使える。Codex でも、仕組みを作り替えずに読める。

## 4. やらないこと（非ゴール）

- **収集データそのものを置くこと。** 出走表、成績、並び、払戻の一覧や CSV、その抜き出しは置かない（Public のため。KEIRIN.JP とオッズパークのサイトポリシー）。
- **選手ごとの特徴の一覧。** 「誰が雨に弱いか」「誰が番手捲りをよくするか」は、今までどおり keirin-data の `watchlist.toml` と keirin-platform の docs/rider-traits.md の側に置く。
- **検証を実行する仕組み。** データの読み込みや集計のコードは keirin-platform に置く（設計者の判断。§7.6）。このリポジトリには、知識と手順を置く。
- **予想モデルの改良。** 知識を使う側の仕事。
- （設計者の判断）**keirin-platform に AGENTS.md を作ること。** オーナーは個人開発で Codex を使っていないので、後続に回す（§10）。

## 5. 失敗とみなすもの（アンチゴール）

技術的に動いていても、次の状態なら失敗とする。

- **保留や未検証のものを、事実として使う。** 通説を結論の根拠にする。
- **公開してはいけないものが入る。** 収集データ、選手名、選手の登録番号、レースと位置から選手を特定できる記述、ビューアの URL、内部 API の呼び出し方の詳細。
- **Claude Code でしか読めない。** 知識のファイルやスキルが Claude Code 専用の仕組みに依存する。
- **新しい巨大な文書になる。** keirin-platform の CLAUDE.md（約350行、増え続けている）のように、書いてあるのに必要なときに効かない。
- （設計者の判断）**オートレースや競馬の言葉が混ざる。** オーナーはオートレースのプロジェクトも並行して進めている。例: 競輪の「1番車」を「1号車」と書く。オートレースの「試走」「ハンデ」の考え方を持ち込む。
- （設計者の判断。autorace-research から引き継ぐ）**AI の自信が増すだけになる。** 手順を通したことを理由に、データから見えないものを無視した結論を強く言う。
- （設計者の判断）**小さな問いにも重い手順を強いて、普段の作業が遅くなる。**

## 6. 制約

- **公開範囲: Public**（オーナー決定）。置いてよいのは、自分たちで集計した統計（件数、割合、検定の結果）と、データのスキーマ（どの表にどの列があり何を意味するか、空の値の意味、いつまで遡れるか）。
  - 個別のレースを例に出すときは最小限にして、出典「KEIRIN.JP」を書く。
  - オッズパークのサイトポリシーは引用も禁止している。並び予想や短評の文言は書かず、集計した値だけにする。
  - 内部 API（keirin.jp の `/pc/json`）の呼び出し方は書かず、keirin-platform の docs へのリンクにとどめる（設計者の判断。robots.txt で許可されていないため。keirin-blog の方針に合わせた）。
  - ビューアの URL と、Private リポジトリの中身（ファイルの内容）は書かない。リポジトリの名前に触れるのはよい（keirin-platform の CLAUDE.md も Public で、名前に触れている）。
- **登録の基準**（オーナー決定）: 広く知られている法則を、自分たちのデータで確かめてから登録する。データが足りず判断がつかないものは、保留にして知識には登録しない。
- **個人差**（オーナー決定）: 選手の名前は出さない。登録するのは「そういう個人差が存在するかどうか」の事実だけ。
  - この規則が及ぶのは keirin-research の中（知識、候補リスト、評価ケース）。keirin-blog の記事は、今までの方針（出典つきで、個別の選手やレースは最小限の例にとどめる）のまま。観察記録は Private の keirin-data に置く（§7.1）。
  - 評価ケースに選手名が要るときは、架空の名前を使う（設計者の判断）。
- **最初の中身の公開**（設計者の判断）: Public なので、PR を push した時点で中身が公開される。v1 で抜き出した中身は、最初の push の前にオーナーに確認してもらう。
- **ツール**（オーナー決定）: 主に Claude Code で使う。Codex は優先度が低いが、Claude Code に限定する仕組みは避ける。
- **言語**: 知識とスキルは日本語。コミットメッセージは Conventional Commits 形式の英語（組織のルール）。
- **進め方**: 組織のルールに従う。PR で進め、GPG 署名は必須、CI が通ったら Claude がマージする（merge commit 方式）。初期コミットだけは main に直接置く。
- **ライセンス**: MIT（設計者の判断。keirin-platform と合わせる。著作権者の表記は shimomo）。
- **動かす場所**: （設計者の判断）v1 はこのマシン（WSL）を前提にする。リポジトリは Public なので、クラウドのセッションでも clone すれば読めるが、v1 では確かめない。

## 7. 決まっている設計

### 7.1 知識の種類と層

autorace-research と同じく、依存する範囲で層に分ける。データの取得元や表が変わったら、下の層だけを差し替えればよい。

1. **ドメイン知識**（どのデータでも共通）
   - **規則・事実**: 公式の資料（業務方法規程、keirin.jp の入門ページ、広報KEIRIN など）で確かめたもの、またはデータの構造で確かめたもの。
     統計的な検証は要らない（設計者の提案。オーナーが会話で了承）。
     例: 級班、競走得点の窓（当月＋前3ヶ月）、昇降級の Δ、ミッドナイトの車番の付け方、4・6・8番車の慣例、決まり手と B・H・S の定義、7車立てと9車立て、ラインと並びの考え方、ガールズにラインがないこと。
   - **レースの仕組み**: 事実をばらばらに並べず、仕組みを軸に束ねる。たとえば「ライン」の項目に、先頭・番手・3番手・単騎の役割、主導権、捲りと番手捲り、競り、地区（府県）でのまとまりを置く。
     仕組みでまとめておくと、初めて見る問いにも要因を持ち込める（F1）。仕組みの説明も、公式の入門ページなどの出典を付けて登録する。
     「〜しやすい」という統計的な傾向は、下の「法則」として扱う。
   - **法則**: 自分たちのデータで確かめた傾向。状態は「確認済み」か「否定」のどちらか（§7.3）。種類は次の2つ。
     - **全体の傾向**: 例: ラインの連動、車番の効果は実力の配置で説明できる、「決勝は堅い」は誤り。
     - **個人差の有無**: 例: 雨での成績に選手ごとの差があるか。選手の名前は書かない（G4）。
   - **用語**: 競輪の言葉と、使わない言い方。オートレースや競馬の言葉が混ざらないようにする（例: 「号車」ではなく「番車」「車番」）。
2. **統計の方法論**（どのデータでも共通）: 有意でないことを差がないと読まない（F5）。比べる前に実力（得点）と構成（種目、車立て、時間帯、級班）をそろえる（F2、F4）。少ない件数は縮小推定で扱う。同じデータで通説を次々に確かめるときの注意。
   autorace-research の方法論のうち競輪に当てはまるものは、競輪の例に書き直して取り込んでよい。どれを取り込むかは作る人に任せる。
3. **取得元ごとの事実**: keirin.jp、オッズパーク。それぞれの癖と、カバーする期間。たとえば、keirin.jp の並びはレース前の予想で、レース後は空になる。オッズパークは過去分の並びが取れるが、10秒間隔で、2026-10-24 から 403 で止まっている。
4. **データごとの記録**: keirin-data のスキーマと期間。
   - 項目ごとの意味、空の値の意味、期間。たとえば収集は 2024-01-01 まで遡っている途中で、2026-12 下旬に完了の見込み。
   - 並びが本物（keirin.jp、オッズパーク）の期間と、府県から推定した並びしかない期間。
   - 予想の学習で使う推定の並びの規則と、その一致率。

層をまたいで、次の4つを持つ。

- **研究の取り決め**: オーナーが決めた約束。たとえば、予想は各選手の1着・3着以内の確率で出し、車券や回収率では出さない。登録と保留の基準（§7.3）。公開してよいものの範囲（§6）。
  **封印期間（誰も見ずに最終確認のためだけに残す期間）は設けない**（オーナー決定、2026-11-01）。代わりに、登録のあとに入ってきたデータで法則を確かめ直す（§7.3）。
- **言葉と項目の対応表**: ファンの言葉とデータの項目を結ぶ。たとえば、ファンの言う「先行」は、データでは脚質「逃」、決まり手「逃げ」、H（最終ホームの先頭）のどれに当たり、それぞれ何を区別できないか。
- **データから見えないもの**: 周回ごとの位置（打鐘、ホーム、バックの隊列）、実際の並び（予想との違い）、レース中の動き（横の動き、仕掛けのタイミング）など。それぞれが結論をどちら向きに歪めうるかを書く。
- **観察記録**（オーナー決定: keirin-data に置く）: オーナーがマルチビューなどの映像で見たこと（日付、場、レース番号、内容、関係する知識の識別子）。
  レースと位置から選手を特定できる記録なので、Public の keirin-research には置かず、Private の keirin-data に置く。
  keirin-research には、観察から一般化した知識（データから見えないもの、言葉と項目のずれ）だけを、観察記録の識別子を出典にして置く。
  keirin-data の中の置き場所と書式は作る人に任せる。

### 7.2 知識1件が持つもの

autorace-research の書式（`## <ID> <題>` と `- <キー>: <値>`）を引き継ぐ（設計者の判断）。どの知識にも次を持たせる。

- **識別子**: 訂正したときに、依存している知識をたどるため。
- **種別**: 規則・事実、仕組み、法則（全体の傾向／個人差の有無）、用語、方法論、取り決め、観察 など。
- **根拠**: 公式の資料なら URL。データで確かめたものなら、§7.3 の検証の記録。
- **成立期間**: いつから、いつまで成り立つか。例: ミッドナイトの得点順の並び（導入は 2020-10 説と 2021-10 説がある）、7車立てが主流になったのは 2020 年後期から、Δ は 2026-06 の点数表の改定後の水準。
- **出典**: keirin-platform の docs など、経緯が書いてある場所。
- **最終確認日。**
- **依存**: 前提にしている知識の識別子。
- 書くのは**いま正しいとされている事実**だけ。経緯は git の履歴と keirin-platform の docs に任せる。

**法則**には、さらに次を必須にする。

- **検証の記録**: 使ったデータの期間、件数、そろえた条件、方法、結果（効果の大きさと区間）。検証に使ったスクリプトの場所（keirin-platform のパスとコミット）。
- **判断が変わりうる条件**: 例: 「本物の並びが1年分そろったら確かめ直す」「9車立てだけで見ると件数が足りない」。

**個人差の有無**には、さらに、選手あたりの件数の分布と、検出力の見積もりを必須にする。

### 7.3 登録と保留

- **登録してよいもの**: 規則・事実（出典つき）、仕組み（出典つき）、データで判断がついた法則。
- **判断がついた**の基準（設計者の判断。§11）:
  - **確認済み**: 効果の 95% 区間が0を含まない。かつ、期間を前半と後半に分けても同じ向きに出る（同じデータで通説を次々に確かめるので、偶然の当たりを減らす）。
  - **否定**: 区間が、事前に決めた「実質的な大きさ」を含まない（効果がないか、あっても実用上は無視できる）。または、通説の言う向きと逆の向きで確認済みの基準を満たす。
  - どちらでもなければ**保留**。
- **確かめ直し**: 封印期間は設けない（オーナー決定）。登録のあとに入ってきたデータは、登録の時点では誰も見ていないので、それで法則を確かめ直す。
  時期は、期替わりのあと（4月・10月の下旬。Δ の再推定と同じ時期）と、本物の並びが1年分そろったとき（設計者の判断）。
  確かめ直して基準を満たさなくなったら保留に戻し、依存する知識を洗い出す。
- **否定も登録する**（設計者の解釈）。判断がついているので、オーナーの「判断がつかないものは登録しない」に反しない。「決勝は堅い」のような誤った通説を AI が使うのを防げる。
- **保留したものは、知識とは別の「候補リスト」に置く**（設計者の提案。オーナーが会話で了承）。
  - 中身: 通説や問いの内容、文献の根拠（遠山競輪研究所などの集計）、なぜ保留したか、前回の試算の結果、判断に要るデータの量、確かめ直す見込みの時期。
  - 目的: 同じ通説を何度も調べ直さないため。また、設計の段階で「確かめるべき要因の候補」として読ませて、ラインのような要因の見落とし（F1）を防ぐため。
  - **候補リストは結論の根拠に使わない**。スキルでそう明記する。
  - docs/keirin-theories.md を候補リストの最初の中身にする。keirin-platform 側の keirin-theories.md は、候補リストへのリンクだけにして二重管理を避ける（設計者の判断。記事のテーマ案としてもリンク先から読める）。
  - 最初の実例: 雨・風の個人差。今は保留。2024-01 までの遡りが終わる 2026-12 下旬に確かめ直す。

### 7.4 作業の段階ごとの手順（スキル）

autorace-research の5つのスキルを、競輪向けに作り直す（設計者の提案。オーナーが会話で了承）。名前と分け方は作る人に任せる。

1. **入口**: 競輪のデータ、選手、レース、予想、分析、記事について話すとき。また、競輪のデータを扱うコードや SQL を書くとき。知識の地図を示し、最初に読むもの（取り決め、用語）を指す。
2. **設計の段階**（調べる、確かめる、集計する、指標や特徴を作る、予想を組み立てる前）
   - 問いをファンの言葉で書く。
   - レースの仕組みから、効きうる要因を挙げる（ライン、位置、主導権、車番の配置、級班と得点の尺度、種目、車立て、時間帯、バンク）。候補リストからも要因を拾う。（F1、F2、F3）
   - 使う項目を対応表で引き、測りたいものとの差を書く。並びが本物か推定か、期間はどこまでかを確かめる。（F6）
   - 比べる前に、実力と構成をそろえる。（F2、F4）
   - この問いに効く「データから見えないもの」を挙げる。
3. **結論の段階**
   - 方法論で見直す。有意でなければ、検出力を書く。（F5）
   - 「データから見えない〇〇の影響を受けうる」を添える。
   - 結論を知識として登録するか、候補リストに保留として残すかを、§7.3 の基準で判断して提案する。
4. **観察との食い違い**（オーナーが映像で見たことと、データの結論がずれたとき）
   - 反論しない。まず「データから見えない要因」か「言葉と項目のずれ」を疑う。
   - データに代わりになる項目がなければ「データでは判定できない」とし、オーナーの観察を keirin-data の観察記録に残す（PR で）。
   - 一般化できる知見があれば、登録の手順で keirin-research に足す（レースを特定できる記述は入れない）。
5. **登録**
   - 下書きをオーナーに見せ、承認を得てから書き込む。
   - 公開してよいものだけになっているか確かめる（§6）。
   - 知識を訂正したら、それに依存する知識と、出典に書かれた使う側の場所を洗い出して一覧にする。

（設計者の判断）単発の集計のような小さな問いでは、設計の段階を短い確認で済ませる。

### 7.5 読ませ方（Claude Code と Codex）

設計者の提案で、オーナーが会話で了承したもの。

- **知識は普通の Markdown** にして、`knowledge/` の下に置く。どのツールでも読める。
- **スキルは SKILL.md 形式**にする（名前と説明を持つ front matter と本文。Claude Code と Codex の両方が読む形式）。
  - スキルの中から知識を指すときは、Claude Code 専用の `${CLAUDE_PLUGIN_ROOT}` を使わず、リポジトリ内の相対パスで指す。
  - スキルの説明文には「競輪」を必ず入れる。オートレースのスキル（autorace-research）と同じマシンに入るので、説明文が似ていると取り違えて読み込まれる。
- **入口は AGENTS.md** にする。リポジトリの中の構成、知識の地図、知識の足し方と公開してよいものの範囲を書く。CLAUDE.md は AGENTS.md を読み込むだけにする。
- **Claude Code のプラグイン宣言**（`.claude-plugin/plugin.json`）は薄い包みとして付ける。導入は autorace-research と同じく、`~/.claude/skills/` へのシンボリックリンクにする。
  知識を足せば、次のセッションからそのまま効く。
- **Codex**: スキルを読み込む場所（ユーザー単位、リポジトリ単位）は、作るときに公式の文書で確かめる。v1 では、手元の Codex でスキルが一覧に出て、知識のファイルを読めることを一度だけ確かめる（設計者の判断。優先度が低いため）。
- **検査ツールは Python の標準ライブラリだけで書く**（autorace-research の `tools/kb.py` と同じ）。書式、識別子、依存、法則の必須キー、公開してはいけないものの検査（例: 6桁の選手登録番号に見える数字）を行う。どのエージェントからでも実行できる。
- **CI**: GitHub Actions で、検査とテストを PR ごとに回す。Public リポジトリなので Actions の利用時間を消費しない（keirin-data の月 2,000 分の上限に影響しない）。

### 7.6 使う側との関係

- **keirin-platform の CLAUDE.md**: 「分析するときの前提」の節を keirin-research に移す。CLAUDE.md には、競輪のドメイン知識は keirin-research にあるという1行と、リンクだけを残す（オーナーが会話で了承）。
  - ほかの節（決定ログ、要望）にある知見は、v1 では知識として登録したものだけを keirin-research に移す。経緯の記述は keirin-platform に残す（autorace-research と同じ、経緯は使う側の docs、事実は知識の側という分担）。
- **keirin-blog の CLAUDE.md**: 同じ1行を足す（設計者の判断）。
- **検証のスクリプト**: keirin-platform に置く（設計者の判断）。データの読み込み（`storage.py`、DuckDB）とテストがそこにあるため。
  - 場所は作る人に任せる（例: `src/keirin/research/`）。
  - 出力は集計値だけにする。選手ごとの行が出る中間結果は、手元か Private の側にだけ置く。
  - 知識の「検証の記録」は、スクリプトのパスとコミットを指す。データが増えたら同じスクリプトで確かめ直せる。
- **keirin-data**: 観察記録のファイルを足す（オーナー決定。§7.1）。
- **v1 はリポジトリをまたぐ**。keirin-research の作成に加えて、次の PR が入る。
  - keirin-platform: スクリプトの追加、CLAUDE.md と docs/keirin-theories.md の書き換え。
  - keirin-blog: CLAUDE.md の書き換え。
  - keirin-data: 観察記録のファイルの追加。
  法則の「検証の記録」は keirin-platform のマージ後のコミットを指すので、スクリプトの PR を先にマージしてから法則を登録する。順序の細部は作る人に任せる。

### 7.7 成功の確かめ方

**再現テスト。** 過去の失敗と同じ依頼を、何も知らない新しいセッションに出し、スキルあり・なしで比べる。
評価のケースはプロンプトと採点基準を書いた Markdown にして、どのツールでも読める形にする。実行には当面 `claude plugin eval` を使う（autorace-research と同じ。`--no-publish` を必ず付ける。子プロセスに API キーが要る）。
依頼文は例で、最終形は作る人に任せる。

| # | 依頼の例 | スキルありで期待すること |
|---|---|---|
| T1（F1） | 「各選手の過去の成績から、次のレースの1着・3着以内の確率を出す方法を考えて」 | 連対率だけで組み立てない。ライン（位置、ラインの人数、単騎）を要因に挙げ、同じラインの選手の着順は独立でない（連動する）ことに触れる。確率で出し、車券や回収率の話にしない |
| T2（F2） | 「1番車が有利かどうか調べて」 | ミッドナイトの得点順の並びと、4・6・8番車の慣例に触れる。得点と時間帯をそろえて比べることを提案する |
| T3（F3） | 「S級に上がったばかりの選手の強さを、競走得点で比べて」 | 窓に前の級班の成績が入っていることと、昇降級の Δ に触れる |
| T4（F4） | 「連日の疲労で、3日目以降は先行が苦しいか調べて」 | 日ごとの種目の構成（初日は予選が多い）をそろえることを提案する |
| T5（F5、G4） | 「雨に弱い選手がいるか調べて」 | 得点と位置で補正したうえで比べる。選手あたりの走数と検出力に触れる。候補リストの前回の試算（保留）を引く。知識や候補リストに残すときは選手名を出さない |
| T6（F6） | 「番手捲りをよくする選手を見つけたい。どう調べる？」 | 並びはレース前の予想であること、本物の並びがある期間、周回ごとの位置がないこと（B・H と決まり手で推定する）に触れる |
| T7 | AI が「この選手は先行で粘れる」と答えた後に、オーナーが「映像では早めに捲られていた」と返す | 反論しない。データから見えない要因と、言葉と項目のずれを疑う。判定できなければ、keirin-data の観察記録に残すことを提案する |
| T8 | 選手名を含む検証結果を渡して「これを知識に登録して」と頼む | 名前を出さない形の下書きを作り、承認を求める。保留か登録かを基準で判断する |

どのテストでも、オートレースや競馬の言葉が出ないこと。

**普段の作業での実感。** オーナーが「ラインのような基本を、言われる前に考慮してきた」と感じられること。

## 8. 最初の中身（v1 の範囲）

v1 が完成したかは、全部を移したかではなく、T1〜T8 を通るかで判断する。残りは、登録の手順で少しずつ足す。

v1 で登録するもの（設計者の案）:

- **規則・事実と仕組み**: keirin-platform の CLAUDE.md「分析するときの前提」（車番）、docs/score-correction.md（窓、級班、Δ）、docs/keirin-theories.md の「前提」の節、ラインの仕組み（公式の入門ページを出典にする）、決まり手と B・H・S の定義。
- **法則**: **ラインの連動**を v1 の中で確かめて登録する。T1 に必要なため。
  - 本物の並び（keirin.jp の 2026-10-05 以降と、オッズパークで取れた分）を使う。
  - 得点だけのモデル（ラインの項を持たないもの）から期待される同じラインの選手の同時入着と、実際とを比べる。
  - 方法の詳細は作る人に任せる。判断がつかなければ、候補リストに置き、仕組み（公式の入門ページ）としてだけ登録する。
  - 車番の効果（実力の配置で説明できる）は、CLAUDE.md の集計を今のデータで確かめ直して登録する。
- **方法論と取り決め**: §7.1 の2. と、研究の取り決め。
- **取得元とデータの記録**: docs/lines.md、docs/data-schema.md、CLAUDE.md の「構成」「データソース」から、性質と期間だけを抜き出す（API の呼び出し方は書かない）。
- **言葉と項目の対応表、データから見えないもの**: T1〜T8 に必要な分。
- **候補リスト**: docs/keirin-theories.md の全項目と、雨・風の個人差。

抜き出すときの決まり。

- **新しい値を採る**。同じ事実について後から書かれた記述（決定ログ、訂正、推定し直した Δ）を探してから書く。
- **データで確かめた数値は、そのときの期間と件数をセットで書く**。docs/keirin-theories.md の「22日分」の集計は参考値なので、法則の根拠にはしない。
- **実装のメモ（画面、コードの構成、ワークフロー）は持ち込まない。**
- 抜き出した結果はオーナーが確認する。

## 9. 作る人に任せること

- スキルの名前と分け方、ファイル構成、識別子の接頭辞。ただし知識は1か所に置き、スキル間で重複させない。
- 知識の書式の細部（§7.2 の項目を満たせばよい）。
- スキルの説明文の書き方（自動で読み込まれる条件）。
- 評価ケースの依頼文の最終形と、採点基準。
- ラインの連動の検証の方法（§8）と、「実質的な大きさ」の決め方（§7.3）。
- 検証のスクリプトの keirin-platform での置き場所。
- 抜き出しの進め方と、オーナーに確認してもらう単位。

## 10. 後続（v1 の外）

- 保留の候補を、データが増えるのに合わせて確かめ直す。まずは雨・風の個人差（2026-12 下旬）と、本物の並びがそろったあとのライン関係の通説（2027-01 ごろ。オッズパークの並びの backfill の再開しだい）。
- keirin-platform に AGENTS.md を作り、Codex からも keirin-research を指すようにする。
- 組織のプロフィール（`.github` の profile/README.md）に載せるかどうか（オーナーと相談する）。
- クラウドのセッションでの利用。

## 11. 設計者の判断（オーナーが決めていないもの）

オーナーの決定ではなく、設計者がこの設計書を書く際に置いた判断。読むときに確かめてほしい。

1. 「確認済み」と「否定」の基準（95% 区間、前半と後半で同じ向き、実質的な大きさ）。
2. 否定された通説も知識として登録する。
3. 検証のスクリプトは keirin-platform に置く。keirin-research には知識と手順だけを置く。
4. docs/keirin-theories.md は候補リストに移し、keirin-platform にはリンクだけを残す。
5. 法則を確かめ直す時期（期替わりのあとと、本物の並びが1年分そろったとき）と、基準を満たさなくなったら保留に戻すこと。
6. keirin-platform に AGENTS.md を作るのは後続にする。keirin-blog の CLAUDE.md にも1行足す。
7. v1 はこのマシンを前提にする。Codex での確認は一度だけ。
8. アンチゴールのうち、オートレースや競馬の言葉が混ざること、自信が増すだけになること、重い手順で遅くなること。
9. 再現テストの依頼文（§7.7）と、v1 で登録するものの一覧（§8）。
10. ライセンスは MIT。
11. v1 で抜き出した中身は、最初の push の前にオーナーに確認してもらう。評価ケースの選手名は架空にする。
